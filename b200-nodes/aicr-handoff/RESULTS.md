## Rail affinity — why the first run of this test was invalid

The job script auto-selects a rail and announced `(auto: PIX to GPU)`. On these nodes that detection is wrong: `nvidia-smi topo -m` shows **no NIC is PIX to the allocated GPU**. Exactly one rail — **`mlx5_4`** — is PXB (same PCIe bridge chain: GPU at `0000:1b:00.0`, NIC at `0000:18:00.0`). All fifteen others are NODE distance, i.e. across the CPU fabric.

Per-rail GPU-memory RDMA (unidirectional), from `eng-rail-19884230.out`:

| Rail | Gb/s | GB/s | affinity to GPU |
|---|---:|---:|---|
| `mlx5_4` | 395.55 | **49.4** | **PXB — same bridge** |
| `mlx5_7` | 148.55 | 18.6 | NODE — cross-CPU |
| `mlx5_8` | 148.52 | 18.6 | NODE — cross-CPU |

A ~2.6x split falling exactly along the affinity boundary. The first run of this counter-test used a NODE-distance rail, so its C3/C4/C5 measured GDRDMA forced through the CPU root complex — not the GPU RDMA path NCCL actually uses. The README warns about precisely this trap (an earlier AICR script hardcoded `mlx5_0`, "a cross-host-bridge path" that "measured the wrong thing entirely").

A queue-pair sweep (`qp-followup.sh`) was run before the cause was known and is retained as a negative result: on a NODE-distance rail, GPU unidirectional went 18.5 / 19.2 / 19.4 / 19.4 / 16.5 GB/s at q = 1 / 2 / 4 / 8 / 16. **Adding queue pairs does not compensate for wrong rail affinity** — the bottleneck is the path, not concurrency.

## Does everything work well on Engaging?

**Yes — the inter-node GPU data path is healthy end to end, with one exception (SHARP), noted below.** Summary of everything measured on these B200 nodes:

| Layer | Result | Status |
|---|---|---|
| GPU compute (gpu-fryer, 3 nodes) | ~97% of the B200 reference, no throttling | OK |
| Intra-node NCCL (NVLink) | all 10 collectives pass on all 3 nodes | OK |
| **GPUDirect RDMA, bidirectional** | **48.7 GB/s per direction** (97.3 total) = ~97% of the 50 GB/s NDR line rate | **OK** |
| Inter-node NCCL (2-node, 8 GPU/node) | sendrecv 49.7 GB/s (~99% of line rate); ring collectives 92-96% of the 400 GB/s node aggregate | OK |
| Megatron-LM 1 / 2 / 3-node | 97-98% of the B200 reference; multi-node weak scaling 98%+ | OK |
| **SHARP in-network reduction** | **unavailable — no `sharp_am` on the fabric** | **NOT ENABLED** |

Two collectives sit far below the fabric ceiling — `gather` (~24%) and `alltoall` (~12%) — but those are documented NCCL algorithm limits, not hardware faults: a ~1.9x faster fabric improved them only 1.05x and 1.19x respectively. See `../out-nccl-2node/summary.md`.

The single genuine gap is **SHARP**, which would remove the two-pass Ring penalty on all_reduce (currently ~60% of the fabric ceiling). That is a fabric-side configuration item, not a defect — see `../sharp.md`.
